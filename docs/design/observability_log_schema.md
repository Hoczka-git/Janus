# JANUS Structured Observability Log Schema

**Status:** Design spec — no implementation  
**Date:** 2026-09-06  
**Scope:** All future structured logging in the Janus codebase  
**Parent research:** t_52aaaa12 (observability findings), prior schema docs in `docs/research/`

---

## 1. Purpose

Define a single, concrete structured log schema for Janus. Every log line produced by the system — whether from CLI dispatch, briefing pipeline, service mutations, or integration calls — conforms to this schema. The schema is a contract: parsers, dashboards, and future automation all depend on it being stable.

This spec supersedes the prior scoped designs (`docs/research/briefing_observability_schema.md`, `docs/observability_log_schema_spec.md`) by generalizing them into a **cross-cutting schema** usable by any module, not just the briefing pipeline.

---

## 2. Serialization format

**JSON Lines (NDJSON).** One JSON object per line, no pretty-printing, no trailing newline requirement. emitted to stderr by default.

```json
{"ts":"2026-09-06T11:00:00.123456+02:00","level":"info","service":"janus.cli","component":"dispatch","event":"command.invoked","trace_id":"abc123","span_id":"span1","data":{"command":"today"}}
```

**Why JSON Lines:**
- Each line is independently parseable — safe for `grep`, `jq`, streaming consumers.
- No multi-line escaping headaches.
- Industry standard for log aggregation (Loki, Elasticsearch, Datadog).

**Encoding:** UTF-8. Non-ASCII characters in string fields are escaped per JSON spec (`\uXXXX`). No binary fields.

---

## 3. Required fields

Every log line must contain these fields. Omitting any of them breaks the contract.

| Field | Type | Example | Description |
|-------|------|---------|-------------|
| `ts` | string (ISO 8601) | `"2026-09-06T11:00:00.123456+02:00"` | Timestamp at emit time. Must include timezone offset or be UTC (`Z`). Microseconds optional but recommended. Generated by the logging layer, not the caller. |
| `level` | string (enum) | `"info"` | Log level. One of: `debug`, `info`, `warning`, `error`, `critical`. Lowercase. |
| `service` | string | `"janus.cli"` | Dotted logger name identifying the emitting module. Convention: `janus.<layer>.<module>` (e.g., `janus.services.attention`, `janus.integrations.telegram`). |
| `component` | string | `"dispatch"` | Optional-subsystem identifier within the service. Falls back to the logger name's last segment if not explicitly set. Allows grouping related events across services (e.g., all `component="dispatch"` events regardless of service). |
| `event` | string | `"command.invoked"` | Stable, dot-separated event identifier in `snake_case`. Identifies what happened. Consumers filter on this field. |
| `message` | string | `"CLI command 'today' invoked"` | Human-readable description of the event. Not machine-parsed. Optional when `data` carries the full context, but strongly recommended for ad-hoc reading. |
| `data` | object \| null | `{"command":"today"}` | Event-specific payload. Always a JSON object when present, never a scalar. `null` when the event carries no structured context beyond the envelope. |

**Field presence rules:**
- `ts`, `level`, `service`, `event`, `data` are always present.
- `component` and `message` are always present but may be empty strings when not applicable (never omitted — a missing key breaks schema-aware parsers).

---

## 4. Optional / contextual fields

These fields appear when relevant. Consumers must treat them as optional.

| Field | Type | Example | When to include |
|-------|------|---------|-----------------|
| `trace_id` | string \| null | `"a1b2c3d4e5f6"` | When the emitting code is part of a traced operation. 32-hex-char UUID4 recommended. `null` when no trace context exists. See §6. |
| `span_id` | string \| null | `"span1"` | When the emitting code is a span within a trace. Short identifier (8–16 chars) unique within the trace. `null` when no span context exists. See §6. |
| `duration_ms` | number (float) \| null | `42.5` | When the event measures an elapsed time. Monotonic clock. `null` otherwise. |
| `error` | object \| null | `{"type":"ValueError","message":"invalid date"}` | When `level` is `error` or `critical`. Carries structured error context. `null` for non-error events. See §5. |
| `correlation_id` | string \| null | `"corr-789"` | Application-level correlation identifier distinct from `trace_id`. Used for cross-system correlation (e.g., briefing_id). `null` when not applicable. |

**No other top-level fields are permitted.** Event-specific structured data goes inside `data`. This keeps the envelope stable for parsers.

## 5. Error field schema

When `level` is `error` or `critical`, the `error` field must be present and structured:

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `type` | string | Yes | Exception class name or error category (e.g., `"ValueError"`, `"TelegramAPIError"`, `"FileNotFoundError"`). |
| `message` | string | Yes | Error message string. Never include secrets, tokens, or full tracebacks. |
| `stack` | string \| null | No | Full traceback as a single string. Only included when the log consumer is expected to debug (e.g., `level=critical`, or when explicitly requested via a diagnostic flag). Omitted in production default. |

Example:

```json
{
  "ts": "2026-09-06T11:00:00.123456+02:00",
  "level": "error",
  "service": "janus.integrations.telegram",
  "component": "send",
  "event": "delivery.failed",
  "message": "Telegram API returned error: chat not found",
  "trace_id": "a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4",
  "span_id": "span1",
  "data": {"chat_id": "123456789", "delivery_type": "daily"},
  "error": {
    "type": "TelegramAPIError",
    "message": "chat not found",
    "stack": null
  }
}
```

## 6. Trace & span context

### 6.1 When to include trace/span

| Scenario | `trace_id` | `span_id` |
|----------|-----------|-----------|
| Single CLI invocation (e.g., `janus today`) | Set once at entry, propagated to all log lines in that invocation | Set at entry, reused for the full invocation (one span per command) |
| Sub-operations within a command (e.g., data collection, Telegram send) | Inherited from parent | New span per sub-operation |
| Service-layer events outside a CLI context (e.g., a library called by a test) | `null` | `null` |
| Independent background jobs (future cron/systemd) | Generated per job run | Generated per job run |

### 6.2 Propagation convention

- `trace_id` is generated once at the entry point of an operation (typically `main()` for CLI commands) and passed explicitly as an optional parameter through the call chain.
- `span_id` is generated at each instrumented boundary (function call that emits log events) and attached to log lines emitted within that boundary.
- Default values are `null` — code that does not propagate trace context emits logs without these fields. This is acceptable; not every log line needs tracing.
- Do not use `contextvars` for trace propagation in the initial implementation. Explicit parameter passing is simpler and more testable for a codebase of Janus's size. Revisit if the call chain depth grows.

### 6.3 Trace ID format

32-character lowercase hex (UUID4). Example: `"a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4"`.

### 6.4 Span ID format

Short, human-readable identifier. 8–16 characters, alphanumeric. Not required to be globally unique — only unique within a trace. Example: `"collect"`, `"score"`, `"send"`.

## 7. Event taxonomy

Events are grouped into categories by prefix. The prefix is part of the `event` field value.

### 7.1 `cli.*` — CLI dispatch

| Event | Level | Description |
|-------|-------|-------------|
| `cli.command.invoked` | info | A Janus CLI command was dispatched. `data` carries `command` and `subcommand`. |
| `cli.command.finished` | info/warning | A CLI command completed. `data` carries `status` (`"ok"` or `"error"`) and `duration_ms`. Use `warning` when status is `"error"`. |

### 7.2 `briefing.*` — Briefing pipeline (daily & weekly)

| Event | Level | Description |
|-------|-------|-------------|
| `briefing.generation.started` | info | Briefing generation began. `data` carries `briefing_type` (`"daily"` or `"weekly"`). |
| `briefing.generation.finished` | info | Briefing generation completed. `data` carries `duration_ms` and summary counts. |
| `briefing.data.collected` | info | Data sources were queried. `data` carries per-source counts. |
| `briefing.attention.scored` | info | Attention engine returned items. `data` carries `item_count`, `category_counts`, `max_score`. |
| `briefing.assembled` | info | Briefing object was constructed. `data` carries `attention_item_count`, `has_suggested_focus`. |
| `briefing.delivery.attempted` | info | Delivery to a channel was attempted. `data` carries `channel`, `destination`. |
| `briefing.delivery.succeeded` | info | Delivery completed successfully. `data` carries `channel`, `duration_ms`. |
| `briefing.delivery.failed` | warning | Delivery failed. `data` carries `channel`, `error`. `error` field must also be populated. |

### 7.3 `source.*` — Data source access

| Event | Level | Description |
|-------|-------|-------------|
| `source.calendar.fetched` | info | Calendar events fetched. `data` carries `calendar_id`, `events_returned`, `parse_errors`. |
| `source.tasks.loaded` | info | Tasks file parsed. `data` carries `file_path`, `tasks_loaded`, `lines_scanned`, `parse_errors`. |
| `source.goals.loaded` | info | Goals file parsed. `data` carries `file_path`, `goals_loaded`, `file_present`, `validation_errors`. |
| `source.workouts.loaded` | info | Workouts file parsed. Same shape as tasks. Contingent on wiring. |

### 7.4 `engine.*` — Internal processing

| Event | Level | Description |
|-------|-------|-------------|
| `engine.attention.computed` | info | Attention items scored and ranked. (Alias/overlap with `briefing.attention.scored` — pick one per implementation.) |

### 7.5 `service.*` — Service-layer mutations (audit trail)

| Event | Level | Description |
|-------|-------|-------------|
| `service.task.mutated` | info | A task was created, updated, or completed. `data` carries `operation`, `task_title`, `previous_state`, `new_state`, `new_progress`. |
| `service.goal.mutated` | info | A goal was created, updated, or completed. `data` carries `operation`, `goal_title`, `changes`. |

### 7.6 `integration.*` — External integration calls

| Event | Level | Description |
|-------|-------|-------------|
| `integration.telegram.send` | info | Telegram API call initiated. `data` carries `chat_id`, `message_length_chars`. |
| `integration.telegram.response` | info/warning | Telegram API response received. `data` carries `api_status`, `api_response_ms`. Use `warning` when `api_status` is `"error"` or `"exception"`. |
| `integration.calendar.error` | error | Google Calendar API call failed. `error` field must be populated. |
| `integration.io.error` | error | File I/O error (missing file, parse error). `error` field must be populated. `data` carries `path`. |

## 8. Data type conventions

| Type | JSON representation | Notes |
|------|---------------------|-------|
| String | `"value"` | UTF-8. Escape control characters. |
| Integer | `42` | No decimal point. Used for counts, IDs, durations in ms. |
| Float | `42.5` | Used for `duration_ms` when sub-millisecond precision is available. |
| Boolean | `true` / `false` | Lowercase, JSON-native. |
| Null | `null` | Used for optional fields when not applicable. Never omit the key. |
| Object | `{"key": "value"}` | Used for `data` and `error` payloads. |
| Array | `["a", "b"]` | Used inside `data` when a field is multi-valued (e.g., `calendar_ids`). |

**Numbers are never strings.** `"duration_ms": "42"` is invalid — it must be `"duration_ms": 42`.

**Timestamps are strings, not numbers.** Always ISO 8601. Do not use Unix epoch seconds.

## 9. Level guidance

| Level | When to use | Example |
|-------|-------------|---------|
| `debug` | Diagnostic detail useful during development, noisy in production. File paths, intermediate values, full request/response bodies (sanitized). | `"debug"`, `"source.tasks.loaded"` with full line-by-line parse details |
| `info` | Normal operational events. Command dispatch, briefing generation, successful deliveries, service mutations. The default level for structured logs. | `"info"`, `"briefing.assembled"` |
| `warning` | Something unexpected but non-fatal. A delivery failed but the command succeeded overall. A data source returned zero events when it usually returns some. | `"warning"`, `"briefing.delivery.failed"` |
| `error` | A failure that prevented an operation from completing. API errors, file not found, parse failures. The `error` field must be populated. | `"error"`, `"integration.calendar.error"` |
| `critical` | A failure that makes the system unable to continue. Only used when the process cannot safely proceed. Rare in a CLI tool. | `"critical"`, process-level fatal errors |

**Rule:** If in doubt between `info` and `warning`, choose `info`. If in doubt between `warning` and `error`, choose `warning`. Over-escalating levels causes alert fatigue.

---

## 10. What never goes in logs

| Material | Reason |
|----------|--------|
| `bot_token` | Credential. Never in any field, including `data`, `error.message`, or `error.stack`. |
| Full exception tracebacks in `error.message` | The `message` field is a short description. Tracebacks go in `error.stack` only when explicitly enabled. |
| Passwords, API keys, OAuth secrets | Credentials. |
| Full file contents | Log counts and summaries, not raw file data. Task/goal titles are acceptable (user data, not secrets). |
| User chat content (messages sent to Janus) | May contain personal data. Not in scope for operational logs. |

## 12. Schema versioning

The schema version is not embedded in every log line. Instead:

- This document is the schema definition. Its file path and revision (git commit hash) identify the schema version.
- Consumers that need to verify schema compatibility should read this document and pin to a git tag or commit.
- If the envelope fields (§3) change, increment a major version and document the migration path in this document's changelog.
- If optional fields (§4) or event types (§7) are added, no versioning is required — consumers ignore unknown fields and events.
